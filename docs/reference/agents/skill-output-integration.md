# Skill Output Integration Contract (Pilot)

Status: experimental. This guide is additive and does not supersede canonical domain schemas or existing skill-local templates.

## Source of truth

- Preserve `schemas/software-engineering/*.schema.json` artifacts and their lifecycle statuses. Do not replace them with execution-result statuses.
- For presentation only, map the canonical artifact through `normalizeLifecycleArtifact` in `scripts/normalize-skill-artifact.mjs`.
- Validate the resulting presentation record with `validateSkillOutput` and render it using `renderSkillOutput`.
- Preserve the complete canonical artifact separately for downstream consumers. A Markdown rendering is not a lossless serialization.
- Never infer test results, approvals, fixed points, source digests, or provenance from a generated summary.

## Pilot route

| Skill | Canonical output | Presentation target | Verification |
| --- | --- | --- | --- |
| `to-spec` | Spec issue and associated work-item metadata | GitHub issue | Acceptance criteria, source issue, non-goals |
| `to-tickets` | Ticket artifacts | GitHub issues | Traceability to spec and dependencies |
| `review-pr` | VerificationArtifact with Standards/Spec axes | PR review/comment | Exact diff fixed point and both axes |
| `plan-review-fixes` | Review repair plan | Markdown or issue | Finding IDs and intended remedy |
| `implement-review-fixes` | Implementation/verification evidence | PR progress | Actual checks, skipped reasons |
| `publish-open-pr` | PR body and validation report | GitHub PR | Linked work, validation, rollback |
| `ship-subissue` | Completion and handoff artifacts | Issue/PR progress | Approval and merge evidence |

This is a mapping specification, **not** a claim that each skill has been migrated.

## Publication safety

1. Generate a preview by default; remote writes require explicit approval.
2. Bind each operation to a stable `target` and `idempotencyKey` scoped to the repository.
3. Implement `findByKey`, `create`, and `update` with authenticated provider APIs and a per-key concurrency guard.
4. On timeouts or ambiguous errors, reconcile the remote state before retrying. Do not blindly duplicate comments.
5. Respect rate limits, permission failures, and cancellation; do not retry authentication/authorization failures.
6. Keep credentials and secret-bearing tool responses out of Markdown and logs.

The generic `publishSkillOutput` helper and `createGitHubCommentAdapter` provide a testable publication interface and GitHub comment mapping, with an authenticated REST client and a same-process concurrency lock, but **not** distributed coordination or guaranteed recovery after ambiguous remote failures. The injected client must set `owned: true` only after checking the comment author against the authenticated account or an explicitly authorized bot identity. A comment marker alone is never proof of ownership. The adapter only supports issue and PR conversation comments, not inline review threads. The publication helper now performs a single read-only reconciliation after an ambiguous comment creation. If the matching owned comment is found with identical content, it reports `reconciled`; otherwise it fails closed and does not retry the write. This does not guarantee recovery when GitHub is eventually consistent or the read fails. Distributed locking, reconciliation of ambiguous updates, and integration into actual skill execution must be implemented and tested before enabling autonomous multi-worker publication.

## Migration rule

Migrate one pilot skill at a time. Retain existing skill-local templates and authoritative schemas, add adapter tests, then compare the old and new output against a golden fixture. A failed or skipped verification cannot become a clean success. Only expand to the next skill after the pilot meets these gates.

## Executable read-only pilot bridge

For a canonical `VerificationArtifact` generated by `review-pr`, preserve the
original JSON file as the downstream handoff. Produce a PR-ready presentation
without changing lifecycle status or the two review axes:

```sh
node scripts/render-lifecycle-artifact.mjs review-artifact.json \
  --title "PR review" --summary "Review evidence and findings" --surface pr \
  --validation validation-checks.json
```

The optional `--validation` file contains an array of
`{"check":"...","status":"passed|failed|skipped","reason":"..."}` records.
`--next-actions` accepts a JSON array of strings. The CLI writes Markdown to
stdout only, does not publish to GitHub, and never edits the canonical source.
A completed canonical artifact is not sufficient evidence for a successful
presentation if checks are failed or skipped; such a combination is rejected.
This pilot is an executable adapter, **not** yet an automatic invocation from
the `review-pr` skill. Source skill instructions, generated registries and
lockfiles remain unchanged.

## Authenticated comment client

`createGitHubRestCommentClient` in
`scripts/github-rest-comment-client.mjs` implements the injected adapter
client using GitHub's REST issue-comment endpoints. Supply a token, repository
owner/name, and the expected authenticated actor login explicitly. Before any
comment read or write, the client checks GitHub's authenticated `/user` endpoint
and rejects a mismatch; the successful identity check is cached per client.
It verifies comment ownership by GitHub's returned author login and independently
fetches the remote comment before every PATCH, refusing updates to comments
owned by another actor. This check does not provide atomic concurrency control. Pair with
`createGitHubCommentAdapter` and `publishSkillOutput`; writes require
`approved:true,dryRun:false`. Same-process locking is available, but
distributed workers can still race. Do not enable autonomous multi-worker
publication until distributed coordination and recovery are tested.

## Review-PR opt-in publication pilot

`presentReviewArtifact` in `scripts/review-pr-output-pilot.mjs` connects the
canonical `review-pr` verification artifact to the normalized presentation and
publication adapter. It accepts only `producer: review-pr` and
`artifactType: verification-artifact`, requires an explicit PR target,
stable idempotency key, and explicit validation results. It preserves the
canonical input, defaults to dry-run, and requires both `approved:true` and
`dryRun:false` before invoking a write. Tests cover previews, unauthorized
writes, producer mismatch, missing verification, and an injected publication
adapter. This is an opt-in application-level integration, **not** automatic
invocation from the canonical skill or authorization for unattended publishing.

Run the pilot test with
`node --test tests/review-pr-output-pilot.test.mjs`.

## Canonical skill registry synchronization gate

The `.agents/skills/**/SKILL.md` files are lock-hashed. Editing one without
regenerating its registry/lock projections causes `validate-skills`, semantic
drift, and conflict checks to fail with `lock hash is stale`. The
`review-pr` integration currently remains an opt-in module and tests rather
than a canonical skill-body edit. Before changing canonical skill text,
regenerate the repository's complete lock and derived views with the
appropriate repository tooling in a fully checked-out worktree; do not
manually forge lock hashes or change generated projections through the
GitHub contents API. Confirm the complete CI matrix afterward.

## Comment identity collision controls

The GitHub comment adapter now refuses publication if a matching idempotency
marker is found in a foreign-owned comment or if multiple owned comments
contain the same marker, including across paginated results. The authenticated
REST client also checks that the existing owned comment ends with the same
idempotency marker as the proposed replacement before PATCH. These checks
prevent accidental adoption of a foreign publication or overwriting a
different publication key. They are not an atomic compare-and-swap: concurrent
writers and malicious edits between GET and PATCH remain outside the
guarantee. Do not enable multi-worker autonomous publication without a
shared transactional lock and an appropriate recovery protocol.

## Injected publication coordination

`publishSkillOutput(record, adapter, {approved, dryRun, coordinator})`
accepts an optional `coordinator` with the interface
`withLock(target, idempotencyKey, asyncCriticalSection)`. The critical
section encompasses the initial remote lookup, mutation, and ambiguous-write
reconciliation. An implementation must provide cross-process mutual exclusion,
lease expiry/fencing, crash recovery, and a stable lock namespace covering
all writers for the same repository and publication key. A plain in-memory
coordinator is **not** a distributed lock. If no coordinator is supplied,
only same-process serialization is provided. This API is an integration
seam, not a claim that distributed publication safety is implemented.

## Migration acceptance gate

Run `node scripts/check-skill-output-coverage.mjs` to verify that every
canonical skill has an assessed classification. Run
`node scripts/check-skill-output-coverage.mjs --require-mapped` for the
stricter release gate: it fails until every entry has the
`mapped-and-verified` status. The current inventory classifier deliberately
does **not** assign that status automatically. Merely mentioning a schema
does not prove that the skill's outputs are compatible or tested. The
strict gate is intended for final acceptance, not for existing baseline CI,
and must not be bypassed by relabeling untested skills.

## Local-host cross-process publication lock

`createFilesystemPublicationCoordinator({directory, waitMs, pollMs})`
in `scripts/filesystem-publication-coordinator.mjs` provides a concrete
coordinator using atomic directory creation. Pass the resulting object as
`coordinator` to `publishSkillOutput`. All publisher processes must use
the same filesystem and lock directory; the filesystem must provide atomic
directory creation. The lock key is a SHA-256 digest of the target and
idempotency key. Lock acquisition times out and fails closed. Locks are
released after the critical section, including when publication fails.

This implementation **does not** provide distributed coordination across
hosts or automatic stale-lock recovery. A process killed while holding the
lock leaves it behind; an operator must establish that the former process
cannot resume and reconcile the remote publication before manually clearing
that lock. Never use this coordinator on independent host filesystems, or
claim it provides fencing. For multi-host deployment, replace it with a
durable transactional coordinator offering fencing tokens and recovery.

## Eight-skill read-only pilot bridge

The `scripts/pilot-skill-output.mjs` module defines presentation surfaces
for `to-spec`, `to-tickets`, `review-pr`, `plan-review-fixes`,
`implement-review-fixes`, `publish-open-pr`, `ship-subissue`, and
`github-project-analysis` (read-only research pilot). It rejects
mismatched canonical producers and disallowed surfaces, maps lifecycle
states to the common envelope, and never invokes remote mutations.

Example:

```sh
node scripts/render-pilot-skill-output.mjs review-pr review.json \
  --title "PR review" --summary "Evidence-backed review" \
  --surface pr --validation checks.json
```

The input must be an existing canonical lifecycle artifact with
`artifactType`, `artifactId`, `operationId`, `status`, and `producer`.
Do not synthesize those fields when a legacy skill does not emit them.
The `--surface json` mode writes a deterministic JSON presentation envelope
to stdout. This is **presentation integration**, not execution of the
underlying skill or proof that all eight canonical producers have adopted
the lifecycle schema. Remote publication remains a separate, approval-gated
operation; `ship-subissue` is never allowed to merge through this bridge.
The end-to-end fixture exercises to-spec rendering, review-pr rendering,
approval denial, idempotent PR comment creation, and local-host locking.

## Canonical lockfile regeneration commands

The canonical skill lock is regenerated by the dedicated maintenance script,
not by the registry synchronization script alone:

```sh
node .agents/skills/skill-dev/lockfile-maintenance/scripts/update-lockfile.mjs --write
node scripts/sync-registry.mjs --write
node .agents/skills/platform/validate-skills.mjs
```

Run these commands in a checked-out worktree after changing canonical
`.agents/skills/**/SKILL.md` files. Review the resulting diffs before
committing. The lockfile tool hashes canonical skill text with SHA-256;
it must not be bypassed by manually inserting hashes. This separation
explains why canonical skill edits without lockfile regeneration failed
previously.

## Evidence-backed catalog migration gate

The strict catalog release gate now accepts `--evidence path/to/manifest.json`.
A manifest entry requires the canonical skill path, SHA-256 of its actual
`SKILL.md` bytes, a tracked `tests/` fixture path and SHA-256 of those
fixture bytes, the output contract identifier, and `result: "passed"`.
The gate recomputes both digests and rejects missing, duplicated, stale,
untracked or failed evidence. Merely adding `mapped-and-verified` to a
classification cannot satisfy the release gate.

Example manifest shape (the hashes below are placeholders, **not**
verification evidence):

```json
{
  "schemaVersion": "1.0",
  "entries": [
    {
      "path": ".agents/skills/research/example/SKILL.md",
      "skillSha256": "<64 lowercase hexadecimal digits>",
      "fixturePath": "tests/example-output.test.mjs",
      "fixtureSha256": "<64 lowercase hexadecimal digits>",
      "contract": "schema/skill-output.schema.json",
      "result": "passed"
    }
  ]
}
```

Run `node scripts/check-skill-output-coverage.mjs --require-mapped
--evidence path/to/manifest.json` only after the corresponding fixture
has actually executed and passed on the same source revision. A digest
proves file identity, **not** that a fixture ran; CI logs or signed test
attestations remain necessary to independently establish execution.

### Executable migration fixture gate

After collecting evidence for **every** canonical skill, run
`npm run output:verify-fixtures -- path/to/manifest.json`. This runner
checks canonical skill and test fixture SHA-256 digests, refuses incomplete
or stale evidence, then executes each unique tracked `tests/*.test.mjs`
fixture using `node --test` with a 30-second timeout per fixture.
The runner reports fixture exit codes and refuses to claim success if
any fixture fails or is missing. The fixture runner intentionally cannot
execute arbitrary commands embedded in a manifest.

A fixture that passes does not by itself demonstrate correctness of the
entire skill. Reviewers must still assess representative behavior, side
effects, trust boundaries, rollback and workflow compatibility. A signed
CI run on the final commit is required for release.

### Behavioral fixture inventory (coverage aid, not migration evidence)

`node scripts/skill-output-fixture-inventory.mjs` produces a deterministic
catalog report for declared behavioral JSON fixtures. It normalizes quoted
frontmatter scalars, accepts only the two repository behavioral-fixture
roots, resolves symlinks before accepting a file, parses the fixture, and
reports missing or unsafe declarations separately. The companion
`tests/skill-output-fixture-inventory.test.mjs` exercises this report.

This report is deliberately **not** an evidence manifest: it does not claim
that a skill has adopted the output envelope, and it cannot satisfy
`--require-mapped --evidence`. Use it to prioritize fixture authoring and
then create real per-skill evidence only after an executable `tests/*.test.mjs`
fixture has passed against the pinned canonical bytes.
